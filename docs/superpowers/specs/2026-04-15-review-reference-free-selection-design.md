# Review Reference Free Selection Design

## 背景

当前回顾编辑器已经支持：

- 通过 `/ref` 命令打开“插入引用”弹窗
- 搜索文章后插入 `{{article_slug}}`
- 搜索文章后插入“内容引用”

前一轮已经把“内容引用”从预切段列表升级到了“正文预览内自由选区”，但交互形态仍然存在明显割裂感：

1. 默认弹窗同时承担“搜索文章”和“阅读正文预览”两类任务，心智不够单一。
2. 搜索列表和正文预览并排显示时，用户在“挑文章”和“读正文”之间频繁切换，视线与注意力被打散。
3. 内容引用本质上是一个二段式动作：先选文章，再进正文选区；把两段动作强行放在同一屏里，会让弹窗显得奇怪。

用户已经明确给出新的目标交互：

- 默认态只保留搜索框和结果列表
- 每条搜索结果直接提供两个 icon 按钮
- 点击“文章引用”立即插入并关闭弹窗
- 点击“内容引用”后，整个弹窗切换为“全宽正文预览”模式
- 预览模式顶部只保留“返回列表”
- 在全宽预览里继续使用自由选区 + 浮动按钮完成插入

本设计的目标，是在保留“自由选区内容引用”能力不变的前提下，把交互结构重新整理成更清晰的“两段式流程”。

## 目标

- 默认弹窗只显示搜索框和结果列表，不再同时显示正文预览。
- 搜索结果列表中每条文章直接提供两个操作入口：
  - 插入文章引用
  - 插入内容引用
- 点击“插入文章引用”后立即插入 `{{article_slug}}` 并关闭弹窗。
- 点击“插入内容引用”后切换到单栏全宽正文预览模式。
- 在正文预览中支持自由选区、浮动“插入引用”按钮和纯文本引用插入。
- 继续优先使用 `content_trans`，为空时回退 `content_md`。

## 非目标

- 不恢复预切段片段选择列表。
- 不在同一视图内同时保留结果列表和正文预览。
- 不把“内容引用”改造成新的页面路由或全屏页面。
- 不记录服务端引用关系，也不新增内容引用历史面板。
- 不实现富文本还原或精准 Markdown 结构还原。

## 当前约束

### 一、正文来源约束

内容引用的数据来源保持不变：

1. 优先 `content_trans`
2. 为空时回退 `content_md`

### 二、引用格式约束

插入格式采用最终确认后的引用样式：

```md
> 这里是你手动选中的正文片段……

—— [文章标题](/article/article-slug)
```

底层交互变更不改变最终写回编辑器的 Markdown 语法。

### 三、页面体量约束

[frontend/pages/reviews/[slug].tsx](/Users/shawn/Documents/GitHub/lumina/frontend/pages/reviews/[slug].tsx) 已经较大，本次应继续把状态与交互压在局部组件中完成，避免继续向页面层堆逻辑。

### 四、已有局部能力可复用

当前已存在两个局部能力，不应推翻重来：

- [frontend/components/ReviewReferenceInsertPanel.tsx](/Users/shawn/Documents/GitHub/lumina/frontend/components/ReviewReferenceInsertPanel.tsx) 已承接引用弹窗
- [frontend/components/ReviewReferenceSelectionPreview.tsx](/Users/shawn/Documents/GitHub/lumina/frontend/components/ReviewReferenceSelectionPreview.tsx) 已承接自由选区正文预览

本次迭代应重构这两个组件的职责边界，而不是新开第三套完全平行的 UI。

## 方案比较

### 方案 A：保留双栏布局，仅继续调宽

优点：

- 实现最小
- 不需要重新组织状态

缺点：

- 交互心智问题没有解决
- “挑文章”和“读正文”仍然混在同一屏
- 用户已经明确表达这种交互“感觉很奇怪”

### 方案 B：列表态 + 全宽预览态切换

默认只显示搜索与结果列表；点“内容引用”后切到单栏全宽正文预览，并通过顶部返回回到列表。

优点：

- 心智最清晰，符合“先选文章，再选内容”的顺序
- 预览态可获得完整宽度，更适合阅读和选区
- 列表态与预览态职责分明，UI 更干净

缺点：

- 需要引入显式视图状态切换
- 需要处理列表态与预览态之间的返回逻辑

### 方案 C：结果列表弹出独立二级抽屉或侧滑层

优点：

- 有层级感
- 动画表现空间更大

缺点：

- 状态和过渡更复杂
- 对当前项目来说收益不如方案 B 明确

### 结论

采用 **方案 B：列表态 + 全宽预览态切换**。

原因：

- 与用户最新描述完全一致
- 保留当前弹窗容器，不需要升级成全屏路由
- 将“选文章”和“选正文”拆成两个单一职责的视图，交互最自然

## 详细设计

### 一、主流程

新的引用插入流程如下：

1. 在回顾编辑器中通过 `/ref` 命令打开引用弹窗。
2. 弹窗默认进入“列表态”，显示搜索框和文章结果列表。
3. 每条结果右侧显示两个 icon 按钮：
   - 插入文章引用
   - 插入内容引用
4. 点击“插入文章引用”：
   - 立即插入 `{{article_slug}}`
   - 关闭弹窗
   - 恢复编辑器焦点
5. 点击“插入内容引用”：
   - 拉取该文章正文
   - 弹窗切换到“预览态”
6. 在预览态中，用户用鼠标自由选中正文片段。
7. 出现有效选区后，在选区附近显示“插入引用”浮动按钮。
8. 点击按钮后，将选中的纯文本引用插入回顾编辑器。
9. 插入完成后关闭弹窗并恢复编辑器焦点。

### 二、列表态结构

列表态只显示：

- 搜索框
- 搜索状态 / 错误状态
- 结果列表

列表态不再显示：

- 右侧文章详情区域
- “已选文章”说明卡片
- 内容引用预览区域
- 文章引用 / 内容引用的大按钮模式区

每条结果项包含：

- 标题
- 可选副标题
- 已选入本期标签（如已有）
- 两个 icon 操作按钮

交互要求：

- 点击文章标题本身不进入详情态，不产生“选中后等待下一步”的中间状态
- 用户应当能直接在结果项上完成动作

### 三、结果项操作

每条结果项右侧提供两个 icon 按钮：

#### 1. 文章引用按钮

行为：

- 直接插入 `{{article_slug}}`
- 关闭弹窗

要求：

- 按钮应有明确 tooltip / `aria-label`
- 应避免误触；视觉上与内容引用按钮区分

#### 2. 内容引用按钮

行为：

- 加载文章正文
- 切换到预览态

要求：

- 若正文加载中，当前结果项或顶部可显示轻量 loading 状态
- 若正文加载失败，在预览态或切换过程中给出错误反馈

### 四、预览态结构

预览态采用单栏全宽布局，不再显示搜索结果列表。

顶部区域包含：

- 返回列表按钮
- 当前文章标题
- “优先使用译文，为空时回退原文”的来源提示

正文区域：

- 占据弹窗主体宽度
- 使用项目现有 Markdown 安全渲染能力显示正文
- 保持足够高度，优先服务阅读与选区

预览态的目标是把用户注意力完全聚焦到“读正文并选一段”。

### 五、返回行为

点击“返回列表”后：

- 弹窗回到列表态
- 清除当前正文选区状态
- 保留当前搜索词
- 保留当前搜索结果列表

不保留的内容：

- 当前预览文章的选区
- 浮动插入按钮状态

这样用户可以快速回到原来的结果集里继续选别的文章，而不用重新搜索。

### 六、正文预览来源

正文预览内容来源固定为：

1. `content_trans`
2. `content_md`

不提供手动切换开关，保持最小复杂度。

### 七、预览渲染方式

正文预览继续复用 [frontend/lib/safeHtml.ts](/Users/shawn/Documents/GitHub/lumina/frontend/lib/safeHtml.ts) 的 Markdown 渲染链：

- 生成安全 HTML
- 维持基本段落、列表、标题等结构感

原因：

- 纯文本会损失上下文结构，不利于用户判断引用范围
- 这次目标是“自由选区”，而不是“恢复原始 Markdown”

### 八、有效选区规则

只有满足以下条件时才显示浮动“插入引用”按钮：

1. 选区发生在正文预览区域内部
2. 选区非空
3. 清洗后的文本非空

允许：

- 跨段落选取
- 跨多个列表项选取
- 任意连续文本范围选取

不做：

- 系统预切段对齐
- 单段限制
- 最大选区段数限制

### 九、选区文本清洗规则

插入时仅保留纯文本，不保留富格式。清洗规则保持为：

1. 使用 `selection.toString()` 读取选中文本
2. 去掉首尾空白
3. 折叠行内连续空格
4. 保留必要换行
5. 超过两个连续空行压缩为两个

### 十、浮动按钮行为

浮动按钮规则保持为：

1. 有效选区出现后，在选区附近显示“插入引用”按钮
2. 选区变化时同步更新按钮位置
3. 选区失效、点击返回、关闭弹窗、切换文章时立即隐藏

### 十一、组件边界

#### 1. `ReviewReferenceInsertPanel`

职责：

- 管理弹窗两种视图状态：
  - `list`
  - `preview`
- 处理文章搜索
- 渲染结果列表
- 处理结果项的两类动作
- 加载文章正文
- 管理从列表态到预览态、以及从预览态返回列表态
- 接收最终插入 Markdown 并回传

#### 2. `ReviewReferenceSelectionPreview`

职责：

- 渲染单篇文章的正文预览
- 监听并管理正文选区
- 显示浮动“插入引用”按钮
- 生成最终内容引用 Markdown 并回传

不再负责：

- 搜索
- 结果列表
- 视图切换

### 十二、测试重点

本轮实现的测试重点应调整为：

1. 列表态源码或组件行为中存在两个结果项操作入口
2. 文章引用动作仍然走 `{{article_slug}}`
3. 内容引用动作会进入全宽预览态
4. 预览态存在返回列表入口
5. 预览态仍然使用自由选区与浮动插入按钮
6. 引用格式与 `content_trans -> content_md` 回退逻辑保持不变

## 风险与处理

### 风险 1：结果项双图标过于拥挤

处理：

- 控制图标按钮尺寸与间距
- 使用 tooltip / `aria-label`
- 保持标题区域与操作区明显分隔

### 风险 2：返回列表时丢失上下文

处理：

- 保留搜索词与结果列表
- 仅清空预览态局部状态

### 风险 3：切换视图时状态残留

处理：

- 从 `preview -> list` 时显式清理选区、浮层位置和当前预览正文
- 从 `list -> preview` 时重新初始化预览态局部状态

## 结论

本次重构不改变“自由选区内容引用”的核心能力，只改变其入口和视图组织方式：

- 默认弹窗回归为纯粹的“搜索与选择文章”界面
- 内容引用改为显式进入“全宽正文预览”模式
- 文章引用与内容引用在结果项层面直接分流

这样可以把交互从“同屏混合模式”整理成“先选文章，再选内容”的清晰两段式流程。
