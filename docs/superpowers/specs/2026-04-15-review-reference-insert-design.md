# Review Reference Insert Design

## 背景

Lumina 当前的回顾编辑能力已经支持两类文章占位机制：

- 旧版总占位符 `{{review_article_sections}}`
- 单篇文章占位符 `{{article_slug}}`

相关入口和渲染逻辑已经存在于：

- [frontend/pages/reviews/[slug].tsx](/Users/shawn/Documents/GitHub/lumina/frontend/pages/reviews/[slug].tsx)
- [backend/app/domain/review_service.py](/Users/shawn/Documents/GitHub/lumina/backend/app/domain/review_service.py)

同时，后台已经具备按标题搜索文章的接口：

- [frontend/lib/api.ts](/Users/shawn/Documents/GitHub/lumina/frontend/lib/api.ts) 中的 `articleApi.searchArticles`
- [backend/app/api/routers/article_router.py](/Users/shawn/Documents/GitHub/lumina/backend/app/api/routers/article_router.py) 中的 `GET /api/articles/search`

但当前回顾编辑仍有两个明显断点：

1. 编辑者虽然可以手写 `{{article_slug}}`，但无法在编辑器里直接搜索文章后插入。
2. 编辑者虽然可以手动复制文章内容做引用，但没有基于文章搜索、片段选择、格式化插入的一体化工作流。

本设计要解决的问题不是重写回顾渲染机制，而是在现有 Markdown 编辑工作流中补齐“搜索文章后插入文章引用或内容引用”的能力。

## 目标

- 在回顾编辑模式中支持搜索文章后插入“文章引用”或“内容引用”。
- 让“文章引用”和“内容引用”共用一次文章搜索流程，避免重复检索。
- 支持命令式触发，满足高频编辑场景下的键盘流工作方式。
- 保持现有回顾占位符渲染机制不变，继续兼容 `{{review_article_sections}}` 和 `{{article_slug}}`。
- 内容引用基于文章正文片段的手动挑选，而不是自动抽取或新增 AI 处理流程。

## 非目标

- 不在本期引入完整的通用 slash command 编辑器系统。
- 不修改回顾保存时的后端占位符校验规则。
- 不新增“摘要引用 / 金句引用 / 要点引用”等 AI 内容引用形态。
- 不引入新的后端数据模型来存储“引用关系”。
- 不把内容引用变成富文本结构化编辑，只生成纯 Markdown。

## 当前约束

### 一、回顾正文保存约束

后端在保存回顾时仍要求正文中保留以下两种形式之一：

- 一个 `{{review_article_sections}}`
- 至少一个 `{{article_slug}}`

相关逻辑位于 [backend/app/domain/review_service.py](/Users/shawn/Documents/GitHub/lumina/backend/app/domain/review_service.py)。

这意味着“内容引用”是现有占位符工作流的补充能力，而不是替代能力。

### 二、文章正文可用字段

前端文章详情类型 [frontend/lib/api.ts](/Users/shawn/Documents/GitHub/lumina/frontend/lib/api.ts) 已经包含：

- `content_trans`
- `content_md`

因此内容引用所需的片段选择可以在前端基于现有文章详情接口完成，无需新增后端引用预处理接口。

### 三、回顾编辑页已较大

[frontend/pages/reviews/[slug].tsx](/Users/shawn/Documents/GitHub/lumina/frontend/pages/reviews/[slug].tsx) 已承载编辑、预览、媒体上传、评论、目录、SEO 等多类逻辑。本期新增能力应尽量抽出局部组件或局部 helper，避免继续把命令面板和片段选择逻辑直接堆入页面主体。

## 方案比较

### 方案 A：编辑器内联插入面板

在编辑器顶部增加一个常驻搜索与插入面板。

优点：

- 实现直观
- 可发现性强
- 改造现有页面成本较低

缺点：

- 与高频 Markdown 编辑的键盘流不够匹配
- 容易让编辑区顶部持续变重

### 方案 B：独立弹窗式插入工具

通过按钮打开一个完整弹窗，在弹窗内完成搜索、选文章、选片段、确认插入。

优点：

- 交互最完整
- 后续扩展引用类型方便

缺点：

- 操作层级较深
- 对重度编辑用户不够快

### 方案 C：命令式插入面板

在回顾编辑器中支持通过命令关键字或工具按钮唤起“插入文章 / 内容引用”面板，并在当前光标位置完成插入。

优点：

- 更符合 Markdown 编辑场景
- 保留按钮入口的同时，熟练用户可完全走键盘
- 能在不引入完整命令系统的前提下完成最小可用命令流

缺点：

- 需要额外处理命令文本替换、插入点、焦点恢复

### 结论

采用 **方案 C：命令式插入面板**。

原因：

- 这是最符合本次需求“继续迭代回顾编辑能力”的方向。
- 它在体验上比纯按钮式更高频友好，又不会像完整命令编辑器那样大幅扩张范围。
- 文章引用与内容引用可以收敛到同一条搜索与插入路径里，复杂度可控。

## 详细设计

### 一、触发方式

本功能采用“双触发、命令优先”的交互方式：

1. 在回顾编辑器中提供一个轻量“插入引用”按钮，作为可发现入口。
2. 在 Markdown 文本框中支持通过命令文本打开插入面板。

本期仅支持最小命令集合：

- `/ref`
- `/reference`

触发条件：

- 光标位于某一行中
- 当前行文本与命令完全匹配
- 由文本输入触发面板打开

按钮触发与命令触发共用同一个面板与插入流程。

### 二、命令替换规则

当通过 `/ref` 或 `/reference` 打开面板时，系统记录当前命令所在行的替换范围。

插入成功后：

- 若当前为命令触发模式，则用最终插入的 Markdown 替换该整行命令文本。
- 若当前为按钮触发模式，则直接在当前光标位置插入 Markdown，不替换已有文本。

边界规则：

- 只替换整行命令，不扫描或替换正文中的普通 `/` 内容。
- 若面板打开后取消操作，原命令文本保持不变。
- 插入内容时自动补齐必要空行，避免与相邻 Markdown 粘连。

### 三、统一文章搜索流程

无论最终插入的是“文章引用”还是“内容引用”，流程都先经过一次文章搜索：

1. 打开面板
2. 搜索文章标题
3. 选择文章
4. 进入模式选择

模式选择包含两个动作：

- `插入文章引用`
- `插入内容引用`

这样可避免“先选插入类型，再重复搜文章”的低效路径。

### 四、文章引用

“文章引用”直接插入单篇文章占位符：

```md
{{article_slug}}
```

说明：

- 继续复用现有后端占位符渲染逻辑。
- 不新增新的 Markdown 语法或引用语义。
- 插入文章引用后，仍然满足后端对单篇文章占位符的保存要求。

### 五、内容引用的数据来源

“内容引用”所用正文来源按以下优先级选择：

1. `content_trans`
2. `content_md`

即：

- 优先使用整理后的译文 / 清洗后正文
- 仅当 `content_trans` 为空时，才回退到原始 Markdown 正文

这样更符合中文回顾编辑场景下的直接引用预期，也能减少中英内容混杂。

### 六、内容引用的片段切分

内容引用不做 AI 摘录，而是基于正文执行前端可解释的段落级切分。

建议规则：

1. 读取正文原始 Markdown。
2. 清理不适合直接作为引用候选的结构噪音：
   - 标题标记
   - 列表前缀
   - 引用前缀
   - 代码块围栏
   - 纯图片、纯链接段落
3. 按自然段进行切分。
4. 过滤不适合作为引用的段落：
   - 过短段落
   - 空白段落
   - 纯 URL 段落
   - 纯代码段
5. 将剩余段落作为候选片段展示。

本期采用“段落级”而不是“句子级”的原因：

- 用户理解成本更低
- 预览与最终插入更一致
- 不需要额外的语言学分句逻辑

### 七、内容引用的选择界面

选中文章并进入“内容引用”后，面板展示该文章的候选片段列表。

每个候选项展示：

- 片段预览文本
- 所属文章标题
- 插入动作按钮

同时保留返回上一步的入口，允许用户返回重新选择文章或改为“文章引用”。

本期不要求：

- 高亮原文章中的实际位置
- 展示“第 N 段”
- 在右侧同时显示完整文章预览

这些都属于后续可扩展能力，不纳入当前范围。

### 八、内容引用的插入格式

当用户选中某个正文片段后，插入到回顾 Markdown 中的格式固定为：

```md
> 这里是你手动选中的正文片段……
-- [文章标题](/article/article-slug)
```

格式约束：

- 第一行为 blockquote 正文
- 第二行为出处行，格式为 `-- [文章标题](/article/article-slug)`
- 不额外插入“来源：”“第 N 段”等元数据

采用该格式的原因：

- 相比“先标题链接、再引用块”，视觉上更接近回顾正文中的标准引文
- 相比只插 blockquote，又能明确出处，便于追溯
- 仍然是普通 Markdown，用户可直接手改

### 九、插入后的编辑器行为

无论插入“文章引用”还是“内容引用”，成功后编辑器行为一致：

1. 关闭插入面板
2. 焦点回到正文编辑框
3. 光标定位到新插入内容末尾
4. 保持单次撤销可回退本次插入

若当前处于命令替换模式，则以替换整行命令后的文本位置作为新的光标点。

### 十、组件边界

本期建议将新增逻辑拆为局部组件和 helper，而不是全部写回 [frontend/pages/reviews/[slug].tsx](/Users/shawn/Documents/GitHub/lumina/frontend/pages/reviews/[slug].tsx)。

建议拆分：

- `ReviewReferenceInsertPanel`
  - 负责命令面板、文章搜索、模式选择、片段列表、插入确认
- `reviewReference.ts`
  - 负责命令识别、片段切分、Markdown 组装、插入文本 helper

页面层仅负责：

- 面板开关状态
- 编辑器 ref
- 当前光标 / 命令替换范围
- 接收最终 Markdown 并更新 `markdownContent`

## 错误处理

### 一、文章搜索失败

- 面板提示搜索失败
- 不关闭面板
- 允许继续修改关键词重试

### 二、文章正文为空

若文章的 `content_trans` 和 `content_md` 都为空或切分后无可用段落：

- 禁用“插入内容引用”
- 或进入内容引用后显示“暂无可引用内容”

但仍允许插入“文章引用”。

### 三、命令触发后取消

- 不移除原命令文本
- 不改变光标位置
- 仅关闭面板

### 四、插入时状态错位

若文章选择、片段选择、当前光标状态已经失效：

- 放弃插入
- 给出错误提示
- 保持已有正文不被改写

## 测试策略

### 一、前端单元测试

针对新 helper 编写测试，重点覆盖：

- `/ref` 与 `/reference` 命令识别
- 命令整行替换范围判断
- 段落切分与过滤
- 文章引用 Markdown 生成
- 内容引用 Markdown 生成

### 二、页面交互验证

重点验证回顾编辑页中的以下路径：

1. 通过按钮触发并插入 `{{article_slug}}`
2. 通过 `/ref` 触发并替换整行命令为 `{{article_slug}}`
3. 通过按钮触发并插入内容引用
4. 通过 `/ref` 触发并替换整行命令为内容引用
5. 取消操作后原命令保留
6. 文章无可用内容时只能插入文章引用

### 三、回归验证

至少确认以下既有能力不受影响：

- 回顾保存
- 回顾预览渲染
- `{{review_article_sections}}` 渲染
- `{{article_slug}}` 渲染
- 媒体粘贴与转存

## 验收标准

- 回顾编辑模式中可通过按钮或 `/ref` 命令打开插入面板。
- 能搜索文章并选中目标文章。
- 选中文章后，可选择“文章引用”或“内容引用”。
- 选择“文章引用”后，会在正确位置插入 `{{article_slug}}`。
- 选择“内容引用”后，会基于 `content_trans` 优先、`content_md` 回退的正文生成候选片段。
- 用户手动选择片段后，插入格式严格为：

```md
> 引用片段
-- [文章标题](/article/article-slug)
```

- 命令触发模式下，插入后会替换整行命令文本。
- 按钮触发模式下，插入后会在当前光标位置追加内容。
- 插入后焦点返回编辑器，且可通过一次撤销回退插入。
- 现有回顾保存校验与占位符渲染保持兼容。

## 实施边界建议

本设计默认先做回顾编辑页范围内的最小闭环，不把命令面板抽象成全站复用能力。若后续文章编辑、评论编辑、Prompt 编辑也出现相同诉求，再把这次形成的命令识别与插入面板抽为通用编辑器能力。
